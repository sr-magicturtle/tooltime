# TOOLTIME

**Schedule the engineering hour, not just the calendar slot.**

TOOLTIME is a working hackathon prototype for [PS1: Railway Track Access Optimisation](PS1/PS1_README.md). It combines a night-control demonstration with a programme scheduler that reads the supplied challenge CSVs. A planner can inspect realistic duration ranges, compare shared setup, simulate a delayed start, review a proposed plan, and export the challenge submission files.

## Run locally

Use Python 3.12 or 3.13. From this folder:

```sh
python -m pip install --target .deps -r requirements.txt
python server.py
```

Open **http://127.0.0.1:8765**. The server loads dependencies from the local `.deps` directory; it also works with the requirements installed in a virtual environment. Internet access is needed for the initial dependency installation. Running the prototype requires no API key or frontend build step.

In the provided Windows workspace, dependencies are already installed. Run `./start.ps1` to restart the app using the bundled Python runtime.

For an environment that already has the requirements installed:

```sh
python server.py --host 0.0.0.0 --port 8765
```

The default host is `127.0.0.1`. The port defaults to the `PORT` environment variable, or 8765 when unset.

## Run with Docker

```sh
docker build -t tooltime .
docker run --rm -p 8765:8765 tooltime
```

Open **http://localhost:8765**. The image includes the public challenge data. It does not copy local dependency caches, runtime uploads, or audit records into the image. The container writes its runtime state under `/app/.runtime`; mount a volume there if audit records should survive container replacement.

The Dockerfile is a deployment starting point. This repository does not include a hosted deployment, authentication, a GitLab repository URL, or a published video. This is a shared-state hackathon application; run a dedicated instance per judging session.

## Two views of the problem

| View | Data | What it demonstrates |
| --- | --- | --- |
| Night control | Explicitly synthetic jobs, readiness records, night times and duration history | Intake, readiness, p50/p90 predictions, agent negotiation, setup sharing, commitment deadlines, approval and team briefs |
| Programme planning | The eight supplied PS1 CSV files, or an uploaded set with the same filenames/schema | Whole-workload scheduling, scenarios A/B/C, constraint checks, completion trade-offs and submission exports |

The public instance has **54 activities, 14 contracts and 192 required access units**, across **76 locations and 30 weeks** starting 4 January 2027. It has 20 station-on-line entries representing 18 distinct station IDs, including two interchange hubs. The original files under `PS1` are retained as the source of truth.

PS1 does not provide historical durations, inventory, crew competencies, plant availability or real first/last-train times. Those extra fields belong to the synthetic night demonstration. A demonstration job held by a readiness check does not remove any activity from the challenge workload.

## What is implemented

- A browser interface and Python API, with live re-planning controls.
- OR-Tools CP-SAT programme scheduling, with locally checked safety and workload rules.
- Quantile duration prediction using scikit-learn gradient boosting at the 0.5 and 0.9 quantiles, trained on 960 synthetic records and evaluated on a separate 240-record synthetic holdout (seed 42). Features include requested duration, system, crew size, isolation, plant and season. Held-out metrics describe the synthetic generator; they are not calibrated estimates for an operational railway.
- A deterministic Reader and role-based negotiation workflow. Reader, Checker, Requester and Planner have distinct responsibilities, but **Gemini and external LLM calls are not integrated**. The visible messages are generated by local rules, not independent Gemini agents.
- Human approval tied to a plan revision, with a written review reason and snapshot reference. Re-planning invalidates the previous approval.
- Downloadable team briefs after approval. Downloading a brief does **not** email or otherwise notify a team.
- Exact three-file challenge exports for a locally feasible solved scenario.

## The two safety clocks

**Latest safe commitment** answers whether a job can still start: handback deadline minus remaining setup, p90 work duration and rollback time.

**Rollback trigger** answers when to stop working and begin restoration: handback deadline minus the time needed to restore the railway. These are different moments. A p90 forecast is a risk estimate, not a guarantee that work will finish. The prototype never treats shared isolation as permission for physically incompatible work to overlap.

The demonstration runs from 00:30 to 05:30 on 5 January 2027. Cable replacement and grinding use separate workfaces in one synthetic electrical zone; CCTV work has no traction dependency. Sharing pays common preparation and restoration once while leaving each job's predicted duration unchanged. Unlike the original illustrative story, cable work can fit alone; the benefit of sharing is that the grinding job can fit as well. The point-machine job stays blocked by stock and competency readiness.

“Tool time” is calculated as scheduled p50 work divided by the full night length times the number of ready crews. Possession efficiency is a separate measure: scheduled p50 work divided by p50 work plus setup and restoration overhead. Neither metric is the percentage of the public challenge workload delivered.

## Programme scenarios and exports

1. Open programme planning and select A, B or C.
2. Run the scheduler and inspect completion, capacity, workload and local validation results.
3. Export the solved scenario as a ZIP containing:
   - `SCHEDULE_ACCESS.csv`
   - `SCHEDULE_OCCUPANCY.csv`
   - `RESULTS.csv`
4. To test another instance, select exactly the eight numbered files `01_LINES.csv` through `08_ACTIVITY_DETAILS.csv`. Uploading replaces the current programme instance and clears its saved solutions. Run each desired scenario again.

| Scenario | Policy |
| --- | --- |
| A | Fixed supply; no ECLO; completion dates may slip |
| B | Fixed planned completion dates; additional capacity and ECLO are permitted |
| C | Balanced trade-off; at most one excess slot per location/week; ECLO constrained to one two-week window per affected line |

Every activity's full workload must be accounted for before a schedule can pass. If a solve cannot produce a complete locally feasible plan, the app reports that outcome rather than exporting an incomplete result as a valid answer. A deadline-feasible Scenario B is not guaranteed for every possible uploaded instance.

The official judging validator is **not included in the information pack**. Validation in TOOLTIME is an independent implementation; a passing result is not official certification. Solver status and scores apply to the implemented model. No global optimality or equivalence to the hidden validator is claimed.

See [challenge notes](tooltime/CHALLENGE_NOTES.md) for known schema ambiguities, conservative interpretations and acceptance checks. In particular, `access_night` is a local contract/type/week accounting index in the export, not a railway-wide calendar night. The scheduler uses a consistent internal possession assignment before producing those local indices.

The live programme solve allows CP-SAT 12 seconds. Its `OPTIMAL` or `FEASIBLE` status refers to this conservative internal model. A checked constructive fallback is used if OR-Tools is unavailable or there is no CP-SAT incumbent; the result identifies that fallback. An incomplete or invalid result is never relabeled feasible. Predecessors conservatively finish in an earlier week than their successors begin.

To regenerate all public scenario files and full local validation reports:

```sh
python tooltime/engine.py --scenario all --seconds 20
```

Results are written under `outputs/A`, `outputs/B` and `outputs/C`, each with the three CSV files and `validation.json`. Inspect each report's `feasible` and `violations` fields before treating its CSVs as submission-ready. The CLI writes its attempted result even if that result is incomplete; the browser export additionally requires local feasibility.

The included public results all deliver 54/54 activities and 192 access units with zero local validation violations:

| Scenario | Local objective | Total contract overrun days | Additional slots | ECLO accesses |
| --- | ---: | ---: | ---: | ---: |
| A | 25.2 | 21 | 0 | 0 |
| B | 30.0 | 0 | 0 | 6 |
| C | 25.2 | 21 | 0 | 0 |

A and C choose the same result on this instance: minor Priority-3 slip costs less than extra interventions. These are measured results from the conservative internal model, with the full reports under `outputs/`.

## Verify the prototype

```sh
python -m unittest discover -s tooltime -p "test_*.py" -v
```

The suite checks scheduling and prediction invariants, real CSV workload accounting, safety and sharing rules, input validation, and HTTP approval/upload/export behavior. API tests use ephemeral local ports and temporary runtime folders, so they do not modify the running demo's audit history or uploads. They also check that a solve finishing after a replacement upload cannot publish a result for the old instance as the current plan.

## Project layout

| Path | Purpose |
| --- | --- |
| `server.py` | HTTP server, API, upload/export and approval state |
| `public/` | Browser interface |
| `tooltime/engine.py` | Challenge data loading, solving, local validation and CSV export |
| `tooltime/intelligence.py` | Synthetic night demonstration, prediction, intake and negotiation |
| `PS1/` | Unmodified challenge statement, eight input CSVs and sample submission |
| `outputs/` | Generated scenario CSVs and local validation reports |
| `.runtime/` | Local audit and uploaded data; created automatically |
| `.deps/` | Optional project-local Python dependencies |
| `DEMO_SCRIPT.md` | Three-minute judging walkthrough |

Audit entries and uploaded files are stored locally in `.runtime`. Current plan approval and programme solutions are held in memory and reset when the server restarts; the audit file persists. The current app has one shared workspace, no user authentication and no operational dispatch integration.
